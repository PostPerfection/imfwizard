# Changelog

## Unreleased

### Changed
- **The GUI preview plays JPEG 2000 through grok**: a picture track file, an IMP directory, a CPL or a directory of codestreams loads into postkit's `GrokPlayer` instead of libmpv, so the frame the step preview draws and the frame playback draws are the same pixels, down to the App 2E tone map and gamut conversion, which both now come from `postkit::preview::display_frame_from_codestream`. A 2K picture track at 250 Mbit/s plays at its own rate where libmpv's ffmpeg jpeg2000 decoder managed a few frames a second and sat black for seconds after a load: a 2048x1080 frame costs 179 ms on one grok thread and the pool of one worker per core sustains 48 frames a second on 16 cores. 4K does not play in real time. The decode resolution menu changes how many DWT levels grok discards, so full, half and quarter no longer reload the file on this path. MP4, ProRes and every other source still play through libmpv, and so does stereoscopic or encrypted JPEG 2000 essence, which `GrokPlayer` refuses by name. Each load prints `[preview] backend: grok|mpv for <path>` to stderr. The QC overlays and the SRT and ASS subtitle tracks work on both. Shared with dcpwizard through the guikit submodule.
- **A raster fit scales and pads on the decoder's own planes**: postkit's picture plan no longer spells `format=gbrp16le` before its geometry, so a `--gpu create` that fits a source onto a named `--raster` crops, scales and pads the planar YUV the decoder hands out instead of packed 16-bit RGB. That plan costs 6.3 CPU seconds over the bare decode on 1442 frames of 2048x872 against 73.0 through the conversion. Every crop and pad offset a plan emits is on the 4:2:0 chroma grid now, so a pillarbox or a letterbox inside the raster sits on an even column and row.
- **grok is pinned at the v20.4.3 release**: every workflow builds the tag instead of a commit on master.
- **The audio level hint measures true peak in Rust**: the hint ran ffmpeg's loudnorm over the whole WAV to read one number off it, 107.7 s on an 888 s six channel 24-bit track. It now calls `postkit::loudness::measure_true_peak_dbtp`, which streams the file and meters each channel on its own thread, 1.0 s on the same track for the same -0.20 dBTP. A WAV the pass cannot read is still skipped by the hint and reported by the encode.
- **`create` gathers its hints beside the encode**: the audio level hint runs ffmpeg's loudnorm measurement over the whole WAV, minutes on a feature length track, and the command waited for it before the first frame was decoded. The hint pass now runs on a thread while the picture encodes and the hints print before packaging. `--check` still waits for them and prints the count as before.
- **The hint and burn rules both wizards carried are postkit's**: every hint rule is `postkit::hints` now, so `hints.rs` only reads the plan into the facts they are decided from, and dcpwizard cannot drift from the thresholds. `subtitle_burn::check_burn_supported` and `BurnTarget` are `postkit::preflight`'s, handed the flag names an IMF user would recognise, `audio_map::input_channels` is gone in favour of `postkit::wav_io::channel_count`, and the CLI's colour-space parser is `postkit::colour::parse_colour_space`, so `colour --source`/`--target` take `dcip3`, `ciexyz`, `bt2020` and `arrilogc`, which used to fall back to Rec.709 unremarked.
- **The audio map parser is postkit's**: `audio_map.rs` hands `postkit::audio_mix_matrix::parse_named_audio_map` the 7.1 lanes and the spellings each answers to instead of walking the `IN:OUT[@GAIN]` grammar itself. `--audio-map` and the GUI matrix take the same names and numbers as before.
- **No grok binary is run any more**: a TIFF sequence handed to `create` or a GUI job is read by postkit's own loader threads, at 8, 12 or 16 bits, and compressed by the linked grok library, which brings a still sequence the per-frame byte cap, a subtitle burn and the overlapped MXF wrap that video already had. DPX, EXR and BMP sequences decode through ffmpeg. `export-frames` decodes each frame in memory and writes the TIFF itself at the codestream's precision; a PNG is 8-bit for an 8-bit codestream and 16-bit, scaled up, for anything deeper. `create` reads a TIFF sequence's raster from the file rather than ffprobe, which cannot read a 12-bit TIFF. grk_compress is gone from `tools`, and CI no longer checks for it.
- **`encode` encodes App 2E codestreams**: it declares the IMF profile and levels for the raster and bitrate and compresses at the bytes a frame that bitrate allows, the way `create` does, where before it passed the bitrate as grk_compress's ratio flag with no profile, so `create` refused its output. Its `--threads` flag is gone, the encoder takes every core. The REST encode job does the same at 250 Mbps.

### Removed
- **The GUI's Target Conversion panel**: it offered to scale, crop or letterbox a source for IMF and ran `target-convert`, which takes a finished IMP and writes a ProRes 4444 .mov delivery master. Fitting a source into an App 2E raster is the Raster control in the Properties panel. `target-convert` itself now fits the picture into the named container and pads it, where it stretched a 2048x1080 picture to 2048x858 before.
- **`imfwizard_core::burnin`**: a re-export of `postkit::burnin` that nothing here called. imfwizard packages a burn through `create --burn-subtitle`, and a caller wanting the standalone pass calls postkit directly.
- **`sdi-preview`**: it set an mpv property mpv does not have and played on screen while claiming DeckLink output. A real SDI path needs ffmpeg or GStreamer built against the Blackmagic SDK, recorded in DESIGN_TODO.

### Added
- **A wide gamut source encodes as Rec.709 RGB**: `create --source-colourspace p3d65`, `rec2020` and `logc`, and the three new entries in the GUI's Source Color Space select, convert every frame into the Rec.709 RGB an App 2E essence descriptor declares, with postkit's `Rec709Transform` linearising on the source's own curve, matrixing into linear Rec.709, clipping each channel to the gamut and encoding at gamma 2.2. All three were refused before, because the only transform there was for them landed on X'Y'Z'. `--source-lut <file.cube>` is applied by ffmpeg's `lut3d` during the decode and its output is now taken as Rec.709 RGB rather than X'Y'Z', so it encodes instead of being refused. `p3` is still refused, since its white is DCI rather than D65 and nothing here adapts a white point, and the refusal sends a D65 master to `p3d65`. `xyz`, `aces` and `acescg` are refused as before. A converting source together with `--hdr` is refused by name, since the conversion lands on Rec.709 SDR while the preset's descriptor declares PQ, and a LUT with `--still-length` is refused because a held still is encoded with no decode for the filter to run in. The end-to-end tests encode a P3-D65 clip and read the picture MXF back: P3-D65 red decodes onto Rec.709 red, a P3-D65 brown moves 137 codes off where it started, and a Rec.2020 grey stays neutral at the level its 2.4 curve re-encodes to.
- **`to-dcp` transcodes an IMP imfwizard made**: the command refused its own output, because it only rewrapped and `create` writes IMF profile Rec.709 RGB where a DCP carries a DCI cinema profile and X'Y'Z'. It now decides from the first frame's codestream header: a cinema profile is rewrapped as before, an IMF profile is decoded frame by frame with `postkit::grok_decoder`, converted to X'Y'Z' by the compressor's own Rec.709 transform and re-encoded under the cinema Rsiz the raster picks, and the run prints `picture: rewrapped, DCI cinema codestreams` or `picture: transcoded Rec.709 RGB to X'Y'Z' cinema 2K at 250 Mbps, 240 frames`. `--bitrate <Mbps>` sets what the transcode compresses at, defaulting to the DCI maximum of 250 and refused above it, and each frame still gets the DCI per-frame byte cap. The picture's ColorPrimaries and TransferCharacteristic are read off the track file: P3-D65 and BT.2020 primaries are refused naming the gamut conversion they need, ST 2084 and the BT.2020 transfer characteristic naming the tone map, an unrecognised UL by its bytes, and a track file signalling nothing is treated as Rec.709 with a warning. A picture edit rate outside the DCI set (24, 25, 30, 48, 50, 60, 96, 100, 120) is now refused on both paths, naming the rate: a 24000/1001 IMP used to rewrap into a DCP carrying that edit rate.
- **`--gpu` and the GPU setting**: `--gpu` on any command runs grok's accelerator plugin for the whole run through `postkit::grok_encoder::use_gpu`, refuses to start when no plugin loads, and logs how many frames the device took at the end. The settings checkbox in the GUI does the same through guikit's `set_gpu` command, off by default. grok finds the plugin through `GRK_PLUGIN_PATH`, the working directory or the executable's directory, and `GRK_NO_PLUGIN` keeps everything on the CPU. The settings dialog's GPU device number is gone, the plugin's in-memory path runs on its first device.
- **The GUI is launched and looked at in CI**: `tests/test_gui.py` runs the built `imfwizard-gui` under Xvfb, waits for a mapped window titled `IMF Wizard` at least 200 pixels a side, reads that window's pixels off the X server and requires more than one distinct value, then sends SIGTERM and requires the process to be gone within 15 seconds having exited 0 or on the signal. A window that never appears, a webview that leaves the window on its configured black, an app that ignores SIGTERM and a crash on the way out each fail with the app's own output attached. The GUI is built in the `gui` job for it, where the job stopped at the Tauri backend's tests before.
- **Line coverage from the Linux CI run**: `cargo llvm-cov --lcov` replaces `cargo test` there, so the same tests run once instrumented, `cargo llvm-cov report --summary-only` writes the per-crate table into the job summary, and `lcov.info` is uploaded as an artifact. macOS and Windows still run plain `cargo test`.
- **`frame-extract` reads encrypted picture essence**: `--key <32 hex chars>` or `--keys-json <KEYS.json>`, where encrypted essence was refused outright before because extraction had nowhere to take a key. The KEYS.json path matches the picture track file's own asset UUID rather than taking the first image key in the file. A key given for an input that is not JPEG 2000 MXF essence is refused rather than ignored, and one given for unencrypted essence warns and goes unused. `--key` leaves the key in the process list, so its help says to prefer `--keys-json`
- **Black and frozen picture is reported after every encode**: postkit runs ffmpeg's `blackdetect` and `freezedetect` on a branch of the decode while the frames compress, and each run it finds comes out as `black picture from 00:00:00:00 to 00:00:02:23 (frames 0 to 71)`, timecoded at the encode's rate. `create` prints them as warnings beside the hints and the GUI writes them into the job log as `[ENCODE]` lines. Both front ends print the same wording, from postkit's `PictureFindings::describe`. A run has to last 2 seconds to be reported, ffmpeg's own default for both filters. A held still, an image sequence and a J2K directory report nothing, since none of them decodes through ffmpeg.
- **A quality target for the J2K encode**: `create --quality-psnr <dB>`, and the GUI Properties panel's Quality (PSNR dB) field, hand grok a PSNR target to allocate layers by instead of a compression ratio. The target is at least 20 and at most 80 dB, refused outside that before anything is encoded. The bitrate (`--bitrate`, the `--profile` preset's, or the GUI's Bitrate field) stops being what the allocation aims at and becomes a per-frame byte cap: 50 Mbps at 24 fps is 260,416 bytes, and a frame the quality target pushes over it is compressed again by ratio to fit, so the cap is a ceiling no codestream passes. Leaving the field blank, or the flag off, keeps the ratio allocation unchanged.
- **LogC sources encode, and a source LUT takes the rest**: `--source-colourspace logc`, and an ARRI LogC3 entry in the GUI's Source Color Space select, go through the same per-frame route P3 and Rec.2020 take, postkit decoding ARRI's LogC3 EI 800 curve before the ALEXA Wide Gamut matrix, with scene linear above 1.0 clipping to white. `--source-lut <file.cube>` is new: ffmpeg's lut3d filter converts the source to X'Y'Z' during the decode and nothing transforms the frames again, so it conflicts with `--source-colourspace`, and a path that is not a file is refused before the encode rather than by ffmpeg partway through it. `aces` and `acescg` stay refused, since they are scene-referred and no matrix reaches X'Y'Z' from them, but the refusal now names the two routes that do convert them: `--source-lut`, and `imfwizard aces --idt <IDT> --odt <ODT>` to convert the source first.
- **The GUI job queue survives closing the window**: every state change is appended to `~/.config/imfwizard/gui-jobs.jsonl` as a JSON line, and the file is read back on start, so a job queued when the app closed is queued again and runs when the worker next runs. `$IMFWIZARD_GUI_JOBS_FILE` points a second app, or a test, at another file. A job that was running when the app closed comes back failed with "the app closed while this job was running", since nothing was left to finish it. The Jobs panel now lists the running job, then the queued ones, then the finished ones newest first, where before it forgot a job the moment it finished, and a failed row carries the reason as its tooltip. Loading rewrites the file with one line per job, so it does not grow without bound. The queue is postkit's `gui_job_queue` and the panel guikit's `jobs.js`, both shared with dcpwizard, so the two wizards queue and list jobs through one implementation.
- **P3 and Rec.2020 sources encode**: `--source-colourspace p3` and `rec2020`, and the same two entries in the GUI's Source Color Space select, go through postkit's per-space matrix on every frame with the compressor transform off, as dcpwizard already does. ACES, ACEScg and LogC are still refused, since they need a rendering transform rather than a matrix.
- **A trim encodes only the frames it keeps**: `--trim-start`/`--trim-end` on a video, and the GUI's Trim fields, turn into the `frame_range` postkit's `EncodeRunOptions` now takes, so trimming five minutes out of a two hour source compresses five minutes instead of two hours and throwing the rest away. The frames before the window are still decoded and discarded, which costs a fraction of compressing them. The codestreams come out numbered from zero and are packaged where the encode wrote them, so there is no `j2k_trimmed` directory of links on this path and no second copy of the essence. A trimmed video can now be wrapped while it encodes as well, since every frame the encoder produces is a frame the composition ships. An image sequence, a J2K directory and a held still are unchanged: postkit narrows only what it decodes frame by frame, so those encode whole and the kept codestreams are hard-linked as before. Sound and timed text are edited after the encode either way.
- **Transport buttons in the preview**: to-start, skip back and forward by 5 seconds, and single-frame step back and forward either side of play, with `,` and `.` as the frame-step shortcuts. Frame stepping pauses playback, as mpv's `frame-step` does. Shared with dcpwizard through the guikit submodule.
- **The picture MXF is written while the encode runs**: `create` and a GUI build hand each finished codestream straight to the wrapper instead of encoding the whole picture, then reading the J2K directory back to wrap it, so packaging no longer pays for a second pass over the essence. The MXF is the same file either way, byte for byte, which is what postkit's overlapped wrap is tested against, and an `--hdr` create carries its ST 2067-21 metadata through it. One predicate decides it before the encode starts, and the log names the reason when the answer is no: a held still and an image or J2K sequence take the encode-then-wrap path unchanged. A cancel or a failure on either side deletes the part-written MXF and leaves the codestreams that finished
- **A playlist that plays packages one after another**: the preview area gained a queue under the scrubber, and a package reaches it from the `+` on a Recent Projects row or the Queue button beside a finished build. A row shows its position and title, moves up or down, comes out, and plays the queue from wherever it is clicked, the row playing carrying a marker and taking the composition title mpv reports once the package is loaded. When a package reaches its last frame the next row loads and starts on its own, off the `eof` the metadata poll now carries rather than a timer of its own. A row plays through the same `previewBuiltPackage` the Play button uses, so a queued package arrives with its packaged subtitle and caption tracks attached and the crop overlay cleared, rather than with the crop of whatever was previewed before it still drawn over the frame. Previewing anything else, from the toolbar or a track's picture, leaves the rows where they are and stops any end of file advancing them until a row is clicked again. The queue lasts the session: nothing is written down and there is no playlist file. Shared with dcpwizard through the guikit submodule.
- **A real retitle for an IMP that is already written**: `retitle --imp <dir> --title <text>`, and the ✎ on each Recent Projects row, rewrite the CPL's ST 2067-3 `ContentTitle` without re-wrapping essence. The CPL gets a new composition id, and the PKL entry (id, new hash and size) and the ASSETMAP entry (id and Path) are repointed at it, so the package stays internally consistent. Track file MXFs keep their asset ids and their bytes. Any KDM or supplemental IMP made from the old composition id stops matching, which the GUI warns about before it runs, and an encrypted IMP is refused outright because a KDM authorises its keys for one named composition id. A signed CPL, PKL or ASSETMAP is rewritten unsigned and named, since the signature no longer covers the bytes. The GUI also renames the folder when it was still named after the old title. The rewriter is `postkit::package_edit`, shared with dcpwizard so the DCP and IMF sides cannot drift. `metadata-edit` is unchanged: it writes a CPL revision annotation, and its `--title` was always the annotation text rather than the ContentTitle, which its help now says.
- **The Recent Projects panel opens a package properly, and starts out of the way**: clicking a row now runs the same open the Open button runs, so the project name, the title field and the timeline read off the package's first CPL instead of only the folder name being copied into the header. The panel is collapsed on first run and the header toggles it, with the last state kept in localStorage so it opens the way it was left. Each row gained a ✎ that retitles the IMP beside the ✕ that deletes it from disk. A supplemental IMP is recorded in the list when it is created, where before only an opened folder and a finished build were.
- **Where the time inside an encode went**: each composition's `[TIMING] encode composition N took` line in the job log is followed by `[TIMING] encode composition N breakdown: decoder wait 12s, frame prep 30s, j2k 4m10s, write 8s`, read off the four cumulative phase clocks postkit's `PipelineProgress` now carries. Frame prep and j2k are summed over the encoder threads, so either can come out longer than the encode's own clock. `create` prints the same four figures when the encode finishes. A held still and an image sequence handed straight to grk_compress time nothing, and the line is left out there rather than printed as four zeros
- `report` carries dcpdoctor's `j2k_codestream_summary` line for an IMP: dcpdoctor d13e0cd scans AS-02 picture tracks frame by frame.
- **The packaged subtitles in the post-build preview**: playing a built IMP loads its timed text on the Sub button, where before the preview opened the package with no subtitle track at all. `packaged_subtitle_file` reads the first CPL of the package, follows the SubtitlesSequence TrackFileId through the ASSETMAP to the track file, unwraps the TTML document out of the AS-02 MXF with asdcplib's timed-text reader and writes it out as SRT under the app cache folder, through the same `read_timed_text_cues` and SRT writer the source-side preview uses. The cue times are the document's own, which is what the package plays at, and the frame rate that reads frame-form times comes from the CPL's composition EditRate rather than the Frame Rate menu. Ancillary resources, the fonts and PNGs a subtitle can carry, are left in the MXF: the preview renders the text alone. A package with no timed-text track leaves the Sub button inert, a package whose CPL or track file cannot be read puts the reason in the status bar, and neither stops the playback.
- **The crop and the subtitles in the preview**: opening the preview on a composition's picture draws the crop the Picture panel holds over the frame and loads that segment's timed text as a subtitle track, so the Crop and Sub buttons in the preview header have something to show. The crop follows the four fields as they are typed and the Auto-crop button as it fills them. TTML/IMSC is written out as SRT under the app cache folder first, through the same `read_timed_text_cues` the trim and the hints read cues with, since mpv renders only SRT, ASS/SSA and WebVTT; SRT and WebVTT are handed over as they stand. A file the preview cannot read leaves the Sub button inert with the reason in the status bar rather than stopping the playback. The post-build preview of the IMP carries no crop, since it is already in its pictures.
- **Picture essence read for the QC report**: `report` runs the verify with `check_picture_details` and `scan_every_frame` on, where `validate` leaves both off and stays fast, and the report now lists the INFO findings beside the errors and warnings, the measured picture bitrate among them.
- **Preview QC controls** (guikit): the embedded preview's header gained a safe-area box (95% or 90%), an aspect mask (1.85, 1.90, 2.39), a centre cross, a thirds grid, a decode-scale select (Full, Half, Quarter, native to J2K through the decoder's `lowres`) and a HUD reading frame, fps, buffer depth and dropped frames. All shared with dcpwizard through the guikit submodule.
- **Post-build Play / Inspect / Reveal**: a finished build shows the three buttons beside the progress bar, so the new IMP can be acted on from where the build was watched. Play opens it in the embedded preview through guikit's `previewDcp`, whose `load_package_dir` takes an IMP directory as readily as a DCP. Inspect switches to the Validate view, points it at the output folder and runs the same validation the Validate button runs, calling that code rather than a second copy of it. Reveal opens the output folder in the file manager. Starting another build clears the row, so a cancelled or failed build never leaves buttons pointing at a package that was not written. The row belongs to the build in front of you: a job picked out of the Jobs list does not bring it back, since `list_jobs` does not carry an output directory.
- **Per-stage timings in the job log**: `run_job` clocks probe, encode, audio map, source edits and packaging, and writes each as `[TIMING] <stage> took <m>m<s>s` next to that stage's own `[ENCODE]` and `[PACKAGE]` lines, per composition, with a `[TIMING] total` at the end. The audio map line appears only when a map ran. The progress event is unchanged: its `elapsed_secs` already carries the encode's own clock from postkit, and the breakdown inside an encode (colour convert against frame prep against the J2K encode) would need a wider payload from postkit, recorded in DESIGN_TODO.
- **Picture bitrate on `create`**: `--bitrate <Mbps>` names the J2K target directly, above 0 and at most 1000, the range the GUI's Bitrate field takes. It wins over the bitrate `--profile` carries and both are logged when they differ. Without either, the encode stays at the 10:1 ratio it has always used. The formula that turns a bitrate into a compression ratio now lives once in `imfwizard-core`'s `compression_ratio_for_bitrate` (raw frame = width x height x 36 bits, 12-bit RGB) and both front ends call it, where the CLI and the GUI each carried their own copy. The GUI keeps its 250 Mbps default.
- **Image sequences reach `create`**: the CLI classifies its `--video` with the same `detect_input_type` the GUI and the preflight use, so a directory of DPX, TIFF, EXR, BMP, JPEG or PNG frames encodes through postkit instead of being handed to the MXF wrapper as codestreams it cannot read. `--fps-num`/`--fps-den` is the rate, since the frames carry none. A picture that is none of the shapes is refused by name from the preflight, listing what is taken, rather than failing later as a size probe that could not read the folder.
- **More GUI frame rates**: the Frame Rate menu gained 23.976, 50, 100, 119.88 and 120 fps.
- **Pre-build check**: `create --check` runs every refusal `create` can make and prints the hints, then exits without encoding or writing anything under `--output`. The refusals now live in one place, `imfwizard-core/src/preflight.rs`, which both front ends call before the encode. Four of them used to fire only after it: App 2E on a J2K directory's codestream (the wrapper's own `precheck_j2k`, now run at plan time too), the source-edit lengths (a delay with no sound, a delay or trim longer than the programme, a trim that leaves no picture), the TTML timing a trim cannot move, and the audio map parse. Each check still lives in the module that owns it and the edit functions run the same pieces, so every message exists once.
- **Pre-build hints**: advisory findings gathered before the encode, taken from DCP-o-matic's thresholds. Audio true peak above -3 dBTP, sound with no language set, a first subtitle before 4 seconds, a cue under 15 frames, cues less than 2 frames apart, more than 3 lines in a cue, and lines over 52 characters (or 79, which replaces the 52 hint). Each rule speaks once for the whole job and names the file and the first offending cue. The CLI prints them as warnings before the encode. The GUI shows them in a "Before you build" dialog with Build anyway / Go back and a "Don't show hints again" checkbox, which Settings > General can turn back on, and writes them into the job log. Nothing here stops a build.
- **Source picture processing**: `create` gained `--crop-left/--crop-right/--crop-top/--crop-bottom` (source pixels, before any rotation), `--auto-crop` with `--auto-crop-threshold` (cropdetect over eight seeked samples, unioned so a dark frame cannot cut into another's picture), `--fill-crop` (crop to the target aspect instead of padding to it), `--deinterlace`, `--denoise`, `--rotate 90|180|270`, `--flip horizontal|vertical|both` and `--raster <WxH>`. The three crops each decide the same thing, so only one may be given. The picture is fitted into `--raster` when one is named and into the source raster otherwise, and a fit is set whenever anything is not the identity, so the encode lands either on an App 2E raster or on the source untouched. The App 2E check consequently runs on the plan's output rather than on the probed source, and both the CLI and the GUI log the plan. A J2K directory is refused, since it never decodes. Held stills run the same filters in their own ffmpeg decode. The Properties panel carries every control plus an Auto-crop button.
- **Audio channel mapping**: `create --audio-map "1:L,2:R,1:C@-6"` routes and mixes the `--audio` WAV's channels, where the destination is a channel name (L, R, C, LFE, Ls, Rs, Lrs, Rrs, or the long labels) or a 1-based number, and the gain is decibels. The highest destination lane sets the output channel count. Several inputs summed into one lane are mixed. A plain routing reproduces its samples bit for bit. The map runs before the audio delay, the trim and the MCA labelling, so the labelled layout describes the packaged file. Without `--audio`, the map reaches the track demuxed from `--video` instead, and a demux that produced nothing is refused naming the source and whether ffmpeg failed to run, refused the file, or the source carries no audio stream at all. The Properties panel carries the map as a matrix of dB cells.
- **Burn-in during the encode**: `create --burn-subtitle <file>` renders the cues into the picture as it encodes, one decode and one encode, instead of the transcode-then-encode the standalone `burn-in` command costs. It reads the formats there is a cue reader for: SRT, ASS/SSA, SCC, FCPXML and MKS/MKV. TTML/IMSC, the format `--subtitle` packages, has no reader and is refused by name rather than silently dropped. `--burn-subtitle-font <ttf/otf>` picks the face. Without one the system fonts are used, and a machine with no font is an error rather than a blank picture. Burnt-in text is part of the image, so it registers no timed-text track, and passing the same file to both `--burn-subtitle` and `--subtitle` is refused. So is burning onto frames that reach the encoder already X'Y'Z' (`--source-colourspace xyz`, or `--hdr` declaring PQ essence), where display-RGB text would land in the wrong colour space, and onto a J2K directory, where nothing decodes. It works on every input shape that encodes: a video, an image sequence (which reaches the frame path through ffmpeg's concat demuxer) and a held still, which encodes once per cue change instead of once per frame. The Properties panel carries both fields.
- **Burn-in appearance**: `create` gained `--burn-font-size` (percent of the frame height), `--burn-colour` and `--burn-effect-colour` (RRGGBB or RRGGBBAA), `--burn-effect none|outline|shadow`, `--burn-outline-width` (percent of the text height), `--burn-line-height` (multiple of the text height), `--burn-margin` (percent of the frame height, from the anchored edge), `--burn-x-scale`, `--burn-y-scale`, `--burn-fade-up` and `--burn-fade-down` (milliseconds). Each is optional and a flag left out keeps the default the rasteriser starts from, 4.5% white text with a black shadow. The values are laid over that default by postkit's `BurnStyleOverrides`, so colours are read by `Rgba::parse_hex`, effects by `parse_burn_effect` and the ranges by postkit, and a bad one is refused before anything opens the source, naming the flag that carried it. An appearance flag without `--burn-subtitle` is refused by its own name. The Properties panel carries all of them except the two scales, which stay CLI-only.
- **A default look for the converted TTML**: `subtitle-convert --font-size <percent>` and `--colour <RRGGBB[AA]>` write a `tts:fontSize` / `tts:color` style that every `<p>` points at, so cues that carry no styling of their own land at that size and colour while a run with its own `tts:color` still wins. The size is a percent of the frame height, written out as a cell-relative length against a declared `ttp:cellResolution="32 15"`, since a bare TTML percentage is read against the parent element's own size and would come out fifteen times too small. Both writers emit it, the flat one and the styled one. Authored TTML is copied unchanged, so asking for either alongside a `.ttml` input is refused rather than silently dropped.
- **Window state restore** — the GUI reopens with the size, position and maximized state it was closed with (tauri-plugin-window-state)
- **Audio delay**: `create --audio-delay <MILLISECONDS>` shifts the sound against the picture, positive later and negative earlier, spelled as in dcpwizard. The running time never changes: a positive delay prepends silence and truncates the same amount off the tail, a negative one drops the head and pads the tail. A delay at least as long as the programme is refused, naming both durations. The Properties panel carries a Delay (ms) field.
- **Source colour space**: `create --source-colourspace <rec709|p3|xyz|rec2020|aces|acescg|logc>`, defaulting to rec709. The value set is postkit's `ColourSpace`. `rec709` reaches the encoder as the `SourceColour::DisplayRgb` the pipeline already used, so today's output is unchanged; `xyz` says the source is already X'Y'Z' and skips every colour transform. The other five have no postkit transform to X'Y'Z' and are refused rather than run through the Rec.709 matrix, which would be silently wrong colour. `--hdr` together with a source the encoder would transform is refused, since the HDR label claims essence nothing rewrote. The dead `prop-colour` select in the GUI is replaced by a real Source Color Space control.
- **Trim**: `create --trim-start <DURATION>` and `--trim-end <DURATION>`, as frames (`48f`) or seconds (`2s`). Picture, sound and timed text move together: cues shift by the head trim, a cue wholly outside the kept range is dropped and one straddling an edge is clamped. Both TTML time shapes are read, clock times (`00:00:01.500`, `00:00:01:12`) and offset times (`0.8s`, `900ms`, `24f`), and each cue is written back in the metric it arrived in. A time that cannot be read, or timing on anything but a `<p>`, stops the trim rather than being moved wrongly. A trim that leaves nothing is refused, naming the source length. The Properties panel carries a Trim fieldset.
- **Still image with duration**: `create --still-length <DURATION>` holds a single image file (dpx, tif, exr, png or bmp) for that long. The image is encoded once and the codestream repeated, so an hour-long slate costs one encode. `--still-length` without a still input and a still input without `--still-length` are both refused. The Properties panel carries a Still Length field.

### Fixed
- **Closing the window during a build stops the build first**: the GUI exited with the encoder threads still compressing, which crashed in grok's teardown, and the seconds the core dump of a multi-gigabyte process took to write looked like the app hanging on close. The close now cancels the running job, records the queued ones cancelled and waits for the worker to stop before the process exits.
- **The file dialogs forgot the last folder between launches**: the GUI kept the folder of the last pick in a variable, so every launch opened the first dialog at the system default again. The folder is stored in localStorage now and the first dialog after a launch opens where the last one closed.
- **Cancelling a build and then closing the app froze it**: postkit's encoder threads left on cancel without closing the frame queue, so the producer waited forever to push into the full queue and the GUI hung on exit behind the blocked job.
- dcpdoctor 34b7c4f -> 0e38987 (v0.5.1): the MXF checks opened every track file with the PCM reader, so asdcplib wrote `PCM file EditRate is not a supported value: 0/0` to stderr for each picture MXF.
- **The encode aimed at a compression ratio and missed the bitrate**: `create`, `encode` and the GUI job divided the encode raster's bytes by the bitrate and handed grok that ratio, but postkit pads the picture to its container before grok sees it, so grok budgeted a bigger frame than the ratio was computed from and overshot. All three now pass the bitrate's bytes a frame, `encode::codestream_byte_cap_for_bitrate(fps, mbps)`, as postkit's `target_codestream_bytes`, and postkit derives grok's ratio from the frame it actually hands grok and gives grok the same number as `max_cs_size`. `encode::target_codestream_bytes_for_job` picks the bitrate the way `compression_ratio_for_job` did, an explicit `--bitrate` over the preset's rate, and a job with neither still encodes at `encode::DEFAULT_COMPRESSION_RATIO`. `compression_ratio_for_bitrate` and `compression_ratio_for_job` are gone, `bitrate_mbps_for_job` stays because the Rsiz sub level is composed from it, and `create` logs `Bitrate 250 Mbps (1302083 bytes a frame)` where it named the ratio.
- **The loudness passes read a packaged sound MXF**: `loudness` and the loudness job opened their input through hound, so a sound track file lifted out of an IMP came back as "wav i/o: Ill-formed WAVE file: no RIFF tag found" rather than a measurement. postkit detects the container by content now and reads a PCM MXF one edit unit at a time, in process with no ffmpeg either way, so measuring a packaged track needs no unwrap first. `--adjust-to` still writes a WAV and still takes one.

### Fixed
- **The GUI job log exists and says what encoded the picture**: `run_job` opened `imfwizard.log` in the output folder before anything created that folder, and threw the error away, so no job ever wrote a log and every line went to stderr, which a desktop launch discards. The folder is created first now, and a folder or a log the job cannot create fails the job with the path in the message. The header gained an `Accelerator:` line reading `off`, `requested, active` or `requested, inactive: <error>` from guikit's `accelerator_status`, and each composition's encode logs `[ENCODE] Frames on the device: <n> of <frames encoded>` from `postkit::grok_encoder::accelerated_frames`, followed by an `[ENCODE] WARNING:` line when the GPU was requested and the device took no frame. A still hold reports no count.

- **`create` wrote a DCP picture in IMF clothing**: every codestream declared the DCI cinema 2K profile (RSIZ 0x0003) and held X'Y'Z' samples, wrapped into an AS-02 track file whose descriptor said nothing about colour at all. - **A fractional frame rate was encoded at a whole one**: the GUI reached the encoder with 29.97 as 30000 frames a second, and once that was folded into the whole rate both front ends shared, a 24000/1001 source still decoded through an ffmpeg `fps=24` filter, so 1439 source frames over a minute came out as 1440 and the composition ran 0.04% long against a CPL that says 24000/1001. postkit's encode now carries the rate as a fraction, and `--fps-num`/`--fps-den` reaches the decode filter, the held still's own decode and the burnt-in subtitle's cue timing as itself. `create` refuses a zero numerator or denominator instead of encoding at one frame a second
